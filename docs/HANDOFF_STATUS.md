## РЕШЕНО — создание задания падало с RLS (см. supabase/016_fix_task_returning_rls.sql)

Настоящая причина найдена и исправлена 2026-08-14 (заняло ~2 дня): `read tasks`
политика использовала `can_view_task(id)`, которая **сама** делает `select ...
from tasks where id = ...`. PostgREST всегда шлёт `INSERT ... RETURNING *`, а
Postgres проверяет SELECT-политику на только что вставленной строке **в
рамках той же INSERT-команды**. По MVCC-правилам команда не видит собственные
ещё не завершённые изменения через отдельный скан той же таблицы — значит
`exists(...)` внутри `can_view_task` всегда находил ноль строк и политика
всегда возвращала `false`, независимо от роли/пользователя. Без `RETURNING`
всё работало (доп. проверки просто не было) — это и сбивало с толку на
протяжении всего расследования (политики/функции/токены/секреты — всё было
идентично и корректно, поэтому все инфраструктурные гипотезы проверялись и
отваливались одна за другой).

Подтверждено экспериментально (как postgres, без RLS вообще):
`with ins as (insert ... returning id) select exists(select 1 from tasks
where id = ins.id) from ins` → `false`.

Фикс: `supabase/016_fix_task_returning_rls.sql` — новая функция
`can_view_task_row(...)`, принимающая колонки строки как аргументы вместо
повторного запроса к `tasks`; `read tasks` политика переключена на неё.
`can_view_task(uuid)` не тронута — она по-прежнему корректна для
`task_attachments` (там нет self-scan проблемы, т.к. запрос к `tasks` идёт
из отдельной, уже закоммиченной строки в отдельном запросе).

Применено и подтверждено рабочим на self-hosted (`api.district-airsoft.ru`).
**На облачном тестовом проекте (`kmijlaxjxipmauhuofph.supabase.co`) миграция
016 пока не применена** — нужно вставить файл целиком в SQL Editor, если
тестовый проект ещё используется.

Debug-логи в `CreateTaskModal.tsx` убраны (были нужны только для этого
расследования).

## Отдельный подтверждённый баг — миграция 010 не применена (НЕ ИСПРАВЛЕНО)

Аудит всех 15 файлов миграций (`supabase/*.sql`) против реальной базы показал: файл
`supabase/010_game_details.sql` целиком не задеплоен (таблицы `game_stages`, `game_attachments`
не существуют, как и их политики + storage bucket `game-attachments`). Из-за этого разделы
«Этапы» и «Файлы игры» в `GameManageScreen` молча показывают пустоту (запрос к
несуществующей таблице проглатывается как `data ?? []`).

Также не задеплоена саморегистрация из этого же файла (политики `commander or self registers
participant` / `commander or self unregisters participant`).

**Фикс готов, но не выполнен пользователем:** содержимое `supabase/010_game_details.sql`
целиком безопасно перевыполнить (`create table if not exists`, `drop policy if exists` перед
create) — просто вставить файл как есть в SQL Editor и запустить.

Внимание: в файле есть `create policy` без предварительного `drop if exists` для
`game_stages`/`game_attachments` (строки после `create table` для этих двух таблиц) — это
безопасно ТОЛЬКО потому что сами таблицы ещё не существуют, значит и политик на них быть не
может. Если это будет перевыполняться повторно после первого успешного прогона — тогда уже
нужно добавить `drop policy if exists` вручную, иначе будет «already exists», как уже было с
`tasks`.

Замечание в сторону: раз одна миграция (010) и одна политика (013) разошлись с репозиторием,
**весь остальной список миграций стоит считать подозрительным**, пока не аудирован явно.
Готовый аудит-скрипт — `migration_audit.sql`, отправлен пользователю файлом в чате ранее
(не в репозитории; при необходимости пересобрать: `grep` по `create (or replace )?function`,
`create policy`, `create table if not exists` во всех `supabase/*.sql`).
